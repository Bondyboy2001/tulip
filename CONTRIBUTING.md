# Contributing

Tulip is a local-first Electron app: an ordinary folder of Markdown files is
the vault, the main process owns the filesystem, and the renderer never touches
it directly. This page is the map — where things live, the contracts between
them, and how to prove a change is safe.

## Layout

```
electron/        the main process — every file, window, protocol and IPC call
  main.js        boot, windows, the vault walk, handlers that stayed close to
                 the shell (large; see "the two big files" below)
  preload.js     the only bridge — named, argument-checked APIs, no generic
                 invoke and no filesystem reach
  vault-contract.json   the vault's file kinds, extensions and name rules,
                 the single source of truth both sides read
  file-kinds.js  which extensions are indexed, reviewed, embeddable, served
  vault-kinds.js the names and predicates derived from the contract
  ipc-*.js       one domain of handlers per file, wired in main.js
  config-keys.js which config keys a renderer is allowed to write, and their
                 shapes — adding a setting means adding it here, deliberately
  code-envs.js / python-env.js   per-note package environments, outside the vault

src/             the renderer — a plain HTML/JS page, no framework
  index.html     the whole shell's markup, commented where roles are unusual
  renderer.js    tabs, the overlay (palette/switcher/search), the panes —
                 large; see below
  *.js           one feature or widget per module (flashcards.js, table.js,
                 match.js, markdown.js, …), imported by renderer.js
  styles.css / controls.css   one stylesheet, custom properties, no pipeline

scripts/         the test suite, benchmarks and build scripts — see Testing
design-qa.md     the review checklist run before design changes ship
```

## The contracts that matter

- **Renderer → main is a named API.** `electron/preload.js` exposes
  `window.tulip.*` — one method per operation, each argument-checked. There is
  no generic `invoke`; a new capability is a new named method plus its IPC
  handler in an `ipc-*.js` domain, not a new channel shape.
- **The vault contract decides file kinds.** `electron/vault-contract.json`
  lists the extensions and name rules; `vault-kinds.js` (names) and
  `file-kinds.js` (index/review/embed/serve sets) project it for main, and the
  renderer reads the same answers over the bridge. Add a file kind in the
  JSON, not in a regex.
- **Main validates everything the renderer sends.** Paths are contained to the
  vault, config writes go through `config-keys.js`'s shapes, and anything that
  runs code requires the vault's recorded trust. A pull request that weakens
  one of those gates needs to say why, out loud.
- **Nothing phones home.** No telemetry, no automatic network. The Copilot
  talks to a provider only after the user has pointed it at one.

## The two big files

`src/renderer.js` and `electron/main.js` are large by accumulation rather than
by accident — features grew in place faster than they were lifted out. Both
shrink one coherent module at a time (`src/match.js`, `electron/file-kinds.js`
and the `ipc-*`/`copilot-*` files were all cut out of them), and that is the
pattern to follow: extract when you are already working inside a block, keep
the module's surface small, and do not split code that is still being argued
about.

## Testing

Most tests are real Electron sessions, not DOM mocks — the scripts under
`scripts/` launch the app against a temporary vault and drive it over CDP.
Commands:

```
npm run lint            # eslint over the JS
npm run typecheck:gate  # the typecheck gate — modules listed must stay clean
npm test                # the whole runner (run-tests.mjs)
npm run verify          # lint + gate + tests, the CI shape
npm run test:a11y       # axe over the shell, settings and the interactive
                        # surfaces — needs `npm run build` first
```

Targeted suites exist per feature (`test:flashcards`, `test:language-table`,
`test:packages-app`, `test:research-app`, …) — run the one your change touches
plus the gate. Tests that need the network or a paid model key are opt-in
(`TULIP_NET_TESTS`, `TULIP_AI_TESTS`); CI never runs them.

## Conventions worth keeping

- Comments in this codebase explain *why*, not what — read a few before
  writing one.
- Keep dependency weight near zero; the app vendors what it renders with.
- Electron's sandbox, CSP and webview confinement are load-bearing. Never
  route around them to make a feature easier.
- Package-manager and release manifests are generated by
  `scripts/release-manifests.mjs` from the CI-built artifacts — do not
  hand-edit them into a release.
